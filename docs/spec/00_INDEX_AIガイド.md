## 2. 情報の信頼度ルール（回答時に必ず守ること）

この仕様書の記述には、根拠の強さを示すタグを付けている。

| タグ | 意味 |
|---|---|
| **[コード確認]** | ソースコードを直接読んで確認した事実。最優先で信頼する。 |
| **[リポジトリ外]** | 引き継ぎ書など文書に書かれているが、このリポジトリのコードでは確認できない事項（例: 勤怠管理プラグイン側の挙動、サーバー運用）。 |
| **[推測]** | コードから論理的に導いた推定。断定せず「と考えられる」と伝えること。 |

**優先順位**: コード確認 ＞ 本仕様書 ＞ `README.md` ＞ `引き継ぎドキュメント.md`（旧）。
旧資料にはコードと食い違う記述がある。食い違いは `11_既知の課題・ドキュメント差異・変更履歴.md` に一覧化してある。

## 3. 回答時の指針（AI向け）

1. **質問者が利用者か、エンジニアかを見分ける。**
   - 画面操作・用語・「どうやるの」→ `02`・`03`・`10` を中心に、専門用語（テーブル名、関数名）を避けて答える。
   - 実装・DB・API・改修→ `04`・`07`・`09` を中心に、ファイル名・関数名・テーブル名・カラム名を示す。
   - 見分けがつかない場合は、まず利用者向けの平易な説明を示し、続けて「技術的な補足」を付ける。
2. **メニュー名・ボタン名・エラーメッセージは画面表示のとおり（日本語）で引用する。**
3. **仕様書にないことは推測で断定しない。** 「この仕様書からは確認できない」と答え、近い情報を示す。
4. **次の点は誤解が多いので注意して答える。**
   - 「社員コード」（人事が決める識別番号）と「内部ID」（DB自動採番）と「乗組員コード」（乗務員を識別する別のコード）は**別物**。
   - 在籍フラグ（在籍中／退職）と退職日は**連動しない**。
   - 乗組員コードは既存社員では**社員編集画面の「新規コードを追加」**からしか変更できない（CSVや通常保存では不可）。
   - マスタ（所属・部署・役職・職種）は使用中だと**削除できない**。
   - 社員を**削除する画面機能はない**（退職扱いにする運用）。
   - マイナンバー欄は画面に「保存時は暗号化されます」とあるが、**コード上は暗号化していない**（`08`・`11` 参照）。
5. 個人情報（マイナンバー等）を含むため、サンプルや回答に実在の個人情報を作り出さないこと。

## 4. 一目でわかる全体像

```
管理画面メニュー「社員情報管理」
 ├─ 社員一覧        … 検索・絞り込み・並べ替え・在籍/退職の切替・一括変更・編集へ
 ├─ 新規社員登録    … 5ステップのフォーム（編集もここで id 指定）

 ├─ CSV出力         … 項目選択・列順・テンプレート保存・形式/文字コード指定
 └─ CSVインポート   … ①基本情報 ②経歴・資格 ③扶養者（ひな形DL→プレビュー→実行）

データ: 13テーブル（社員1件 ＋ 保険/退職(1:1) ＋ 学歴/職歴/資格/扶養者(1:多) ＋ 乗組員コード履歴 ＋ マスタ4 ＋ CSVテンプレート）
公開API: emp_get_active_employees() ほか（勤怠管理など他プラグインが利用）
```

## 5. 機密情報の扱いについて

元の引き継ぎ書にはサーバー接続情報（ホスト名・DBユーザー名・SSH情報など）が含まれる。**本仕様書セットにはそれらを転記していない。** NotebookLM等へアップロードする資料に認証情報・接続情報を含めないこと。
